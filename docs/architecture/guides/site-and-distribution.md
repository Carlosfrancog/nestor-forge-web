# Site e distribuição

## Papel do site

`site/` é uma interface estática da geração de agentes. `index.html` oferece edição guiada ou JSON e escolha entre Codex, Claude e ambos; `app.js` monta a spec e inicia `forge-worker.js` ([`site/index.html:41`](../../../site/index.html#L41), [`site/index.html:105`](../../../site/index.html#L105), [`site/index.html:113`](../../../site/index.html#L113), [`site/index.html:12`](../../../site/index.html#L12), [`site/app.js:316`](../../../site/app.js#L316)). **Inferência:** é uma interface de entrega da capacidade descrita em [Geração de agentes](agent-generation.md), não um compilador separado, pois o worker importa `ForgeCompiler` do pacote Python copiado para o build ([`site/forge-worker.js:42`](../../../site/forge-worker.js#L42), [`scripts/build_site.py:76`](../../../scripts/build_site.py#L76)).

O formulário guiado inicia com permissões conservadoras e campos de lista vazios; o modo JSON aceita uma spec completa e pode importar arquivo local. Antes de gerar, `validate` exige `name`, `role` e `mission`, confere listas conhecidas e o formato preferido ([`site/app.js:18`](../../../site/app.js#L18), [`site/app.js:116`](../../../site/app.js#L116), [`site/app.js:170`](../../../site/app.js#L170), [`site/app.js:215`](../../../site/app.js#L215), [`site/app.js:295`](../../../site/app.js#L295)).

## Fluxo no navegador

1. Ao clicar em compilar, a página envia ao worker a spec, o destino, um slug e um prompt de continuação específico do destino ([`site/app.js:203`](../../../site/app.js#L203), [`site/app.js:316`](../../../site/app.js#L316)).
2. Na primeira execução, o worker importa Pyodide de um CDN e busca cinco arquivos do núcleo Python publicados junto ao site. A promessa é reutilizada nas gerações seguintes e limpa em caso de erro de carregamento ([`site/forge-worker.js:2`](../../../site/forge-worker.js#L2), [`site/forge-worker.js:5`](../../../site/forge-worker.js#L5), [`site/forge-worker.js:13`](../../../site/forge-worker.js#L13), [`site/forge-worker.js:20`](../../../site/forge-worker.js#L20)). Portanto, há dependência de rede no primeiro carregamento do runtime, mesmo que a compilação ocorra no navegador.
3. O Python embutido escolhe `ClaudePluginRenderer` para `claude`, `UnifiedProjectRenderer` para `unified` e o formato genérico para `codex`; compila, grava arquivos e acrescenta `spec.json` e `PROMPT_<DESTINO>.txt` ao pacote ([`site/forge-worker.js:37`](../../../site/forge-worker.js#L37), [`site/forge-worker.js:52`](../../../site/forge-worker.js#L52), [`site/forge-worker.js:55`](../../../site/forge-worker.js#L55)). No caso Codex, o ZIP genérico é uma base para adaptação guiada pelo prompt; no caso unificado, já há entradas `.agents`, `.claude` e `.codex` ([`site/app.js:203`](../../../site/app.js#L203), [`nestor_forge/targets.py:147`](../../../nestor_forge/targets.py#L147)).
4. O worker compacta os arquivos sob uma pasta com o slug e transfere os bytes à página. `app.js` cria uma URL de objeto para download e exibe o prompt ([`site/forge-worker.js:59`](../../../site/forge-worker.js#L59), [`site/forge-worker.js:64`](../../../site/forge-worker.js#L64), [`site/app.js:229`](../../../site/app.js#L229)). O worker reporta erro à interface quando a geração lança exceção ([`site/forge-worker.js:66`](../../../site/forge-worker.js#L66), [`site/app.js:247`](../../../site/app.js#L247)).

**Ponto a alinhar:** a lista fixa “Conteúdo do ZIP” promete “Relatório de geração” para todos os destinos, mas `BUILD_REPORT.md` pertence apenas ao renderizador genérico; Claude e unificado recebem seus próprios arquivos de destino mais spec e prompt ([`site/index.html:122`](../../../site/index.html#L122), [`nestor_forge/compiler.py:28`](../../../nestor_forge/compiler.py#L28), [`site/forge-worker.js:52`](../../../site/forge-worker.js#L52)).

## Montagem e pacote de agentes

`scripts/build_site.py` copia o site para `dist/site`, injeta versão e ação de download da extensão no HTML e copia os cinco módulos Python buscados pelo worker ([`scripts/build_site.py:18`](../../../scripts/build_site.py#L18), [`scripts/build_site.py:68`](../../../scripts/build_site.py#L68), [`scripts/build_site.py:76`](../../../scripts/build_site.py#L76)). Se houver VSIX em `dist/` com nome da versão, o build confere `name`, `publisher` e `version` internos, copia o pacote para `downloads/` e escreve `updates/agentorchestra.json` com URL, hash SHA-256 e tamanho. Sem VSIX, o HTML informa que o download está indisponível ([`scripts/build_site.py:27`](../../../scripts/build_site.py#L27), [`scripts/build_site.py:37`](../../../scripts/build_site.py#L37), [`scripts/build_site.py:48`](../../../scripts/build_site.py#L48), [`scripts/build_site.py:63`](../../../scripts/build_site.py#L63)).

O mesmo build gera `downloads/agentes-contexto-importavel.zip`. `scripts/build_context_agents.py` lê as três specs em `examples/context-agents/` (`leitura-de-projeto`, `historico-git`, `contexto-de-stack`), chama `scripts/agent_run.py` com `unified-project` para cada uma, acrescenta as specs de origem e uma nota de instalação e exporta o pacote pela rotina de compartilhamento da extensão ([`scripts/build_site.py:74`](../../../scripts/build_site.py#L74), [`scripts/build_context_agents.py:16`](../../../scripts/build_context_agents.py#L16), [`scripts/build_context_agents.py:40`](../../../scripts/build_context_agents.py#L40), [`scripts/build_context_agents.py:58`](../../../scripts/build_context_agents.py#L58), [`scripts/build_context_agents.py:70`](../../../scripts/build_context_agents.py#L70)). A página liga esse ZIP à seção de instalação da extensão ([`site/index.html:165`](../../../site/index.html#L165)).

O workflow de Pages, em push para `main` ou execução manual, empacota o VSIX, monta o site e publica `dist/site`; seus comandos e verificações estão detalhados em [Entrega e verificação](delivery-and-verification.md) ([`.github/workflows/pages.yml:3`](../../../.github/workflows/pages.yml#L3), [`.github/workflows/pages.yml:28`](../../../.github/workflows/pages.yml#L28), [`.github/workflows/pages.yml:38`](../../../.github/workflows/pages.yml#L38), [`.github/workflows/pages.yml:42`](../../../.github/workflows/pages.yml#L42)). O empacotamento da extensão copia o núcleo Python para `vscode-extension/vendor/nestor_forge` por meio do passo `vscode:prepublish` ([`vscode-extension/package.json:21`](../../../vscode-extension/package.json#L21), [`scripts/bundle_extension_backend.py:5`](../../../scripts/bundle_extension_backend.py#L5)).

## Limites da validação

O repositório contém testes escritos para a montagem do site, presença dos módulos Python, ZIP de agentes e manifesto de atualização, além de um teste de navegador em `tests/browser_smoke.mjs` ([`tests/test_forge.py:140`](../../../tests/test_forge.py#L140), [`tests/test_forge.py:154`](../../../tests/test_forge.py#L154), [`tests/test_forge.py:183`](../../../tests/test_forge.py#L183), [`tests/browser_smoke.mjs:21`](../../../tests/browser_smoke.mjs#L21)). **Não verificado nesta leitura:** resultado atual desses testes, download real do Pyodide, execução do worker em navegadores alvo, integridade do ZIP após download e publicação real no GitHub Pages. O fluxo de publicação e os arquivos distribuídos foram inspecionados estaticamente.
